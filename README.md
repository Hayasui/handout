# handout

本仓库把结构化 markdown 渲染成排版齐整的 docx 与 A4 打印用 PDF。输入是干净的源文件，输出是可直接打印的成品，供做现场主持人手册、访谈脚本、评分卡与观察记录表的人使用。

用研材料里有一类材料需要拿在手上用：现场主持人手册、访谈脚本、评分卡、观察记录表。它们的共同要求是打印出来就能照着念、照着记：句子或段落不能跨页断开；中英话术上下对齐，主持人讲中文、念英文；有些内容不能让玩家看见，要用边框或底色标出；有些地方要留出能写字的空档。这些要求都落在版式上，而版式不该写进源文件。源文件保持成干净的标准 markdown，长什么样由渲染器决定。

## 一次解析，两条渲染线

渲染器先把 markdown 解析成一个元素列表，再拿同一份列表出两样东西。docx 走 python-docx，出来的是能在 Word 里改的副本；PDF 走「生成一份带打印样式的 HTML，交给 Edge 的无头模式打印」，出来的是定稿外观。

两条线的分页不保证逐页一致。这是两条独立排版引擎的必然结果，不必试图对齐：**打印以 PDF 为准**，docx 当可编辑副本。核对时比页数与正文文字，不要比字节。

## 版式由栏名触发，不由标记触发

早先的做法是在 markdown 里写自定义标记，像 `[[lines:N]]` 表示这里要画几条横线，或者用 `> [!WARNING]` 表示套红框。这套做法已经废掉，理由是它把排版知识漏进了源文件：源文件本该是内容，标记是工具的实现细节，混在一起，读的人要先学会这套标记才能改文档。

现在的做法是认栏名。「观察记录点」这五个字出现，渲染器就在它下面的内容之后补手写横线；「内部提醒」「内部参考词库」「记录清单（主持人用）」「提示清单（主持人用）」出现，那一块就套浅红框；二级标题出现，起新页。想让某个栏名换一种呈现，改渲染器的配置，源文件一个字不动。

这条约定还有一层好处：源文件是标准 markdown，谁都能读、谁都能改，不依赖任何工具。

## 保真校验是可选的

手册这类文件常常不是手写的，而是从别的文件（中文定稿、英文定稿、旧版需求）提取重组的。机器搬内容，最怕它悄悄改词、漏句、或者自作主张补一句：定稿是审过的，派生物一旦自己改了词，念出去的就是没人审过的话。

用 `--ref` 给出源头文件，渲染完就会顺带做一次逐字回查：markdown 里每一句中英双语行，都要能在源头文件里原样找到，找不到的连行号一起报出来。不给 `--ref` 就跳过，自己手写的 markdown 不需要这道检查。

它只查「找不到」，不查「意思变了」。同义替换、语序调整、语义走样一律看不出来，只有逐字照抄才能过关。这是它的局限，也是它的用处。

## 目录

```
SKILL.md                            主流程（什么时候用、怎么跑、源文件怎么写、版式怎么改）
references/
  markdown-conventions.md           渲染器认哪些写法：标题、双语行、栏名、表格、已废标记
  layout-spec.md                    版式默认值：页面、字号、颜色、手写横线、分页的做法与改法
  environment.md                    本机渲染链：python 用哪个、Edge 怎么调、为什么走 ASCII 中转
scripts/
  render_handout.py                 渲染器主体：解析 → docx + PDF，可选带保真校验
  verify_fidelity.py                保真校验：双语行逐字回查源头文件
examples/
  job.example.json                  job 配置的样子
```

## 用法

写一份 job 配置，把路径、输出名、横线例外、源头文件都写进去：

```json
{
  "md": "…\\【2609】3D二合主持人手册.md",
  "out_dir": "…",
  "stem": "【2609】3D二合主持人手册",
  "title": "3D二合 现场主持人手册",
  "lines": 4,
  "lines_rules": { "环节 4": 8 },
  "refs": ["…\\3D二合北美有人访谈大纲.md", "…\\3D二合北美有人访谈大纲_EN.md"],
  "verify": true,
  "q_range": "2-33"
}
```

```
<python> scripts/render_handout.py --config job.json
```

也可以全走命令行，`--md` 是唯一必填项：

```
<python> scripts/render_handout.py --md 手册.md --out-dir . \
    --lines 4 --lines-rule "环节 4=8" --ref 定稿.md --ref 定稿_EN.md
```

`python` 要用装了 `python-docx` 的那个解释器。跑完会有一份报告，写明元素统计、分页锚点、两份产出的字节数，以及校验结果。`q_range` 在保真校验打开时才生效，用来顺带检查题号有没有缺号。

## 定下来的几条原则

这是渲染工具，不是编辑工具。markdown 是源头，docx 与 PDF 是产物。源文件里的措辞一个字不改，读起来别扭、版式被挤开，都去改源文件，不在渲染器里做特例。

分页交给渲染器，别让写文档的人靠空行或分页符去调页。二级标题起新页就够了，剩下的交给引擎，页尾留点空档，比断在半句话上可接受得多。

两条线各自最优，不追求字节一致。docx 用厘米与磅，HTML 用毫米与 pt，两边的数值本是分别调的，改版式时两边都要看一眼，别指望改一处两边同时变。

还有一类经验值得单独记下来：这台机器上 Word 没装、WPS 的 COM 被拦、bash 起不来、PowerShell 抓不到原生命令的输出。这些会反复绊人的事写进 `references/environment.md`，不靠记性。

## 使用前提

Python 3.8 以上，需要 `python-docx`（出 docx）与 `pypdf`（核对分页时用）。
PDF 依赖 Microsoft Edge 的无头模式，Windows 上是默认路径；换机器或换系统时用 `--edge` 指定。
